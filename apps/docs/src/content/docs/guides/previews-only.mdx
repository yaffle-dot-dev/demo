## Why start with previews?

You're already running Terraform or OpenTofu in production—maybe with Atlantis, Terraform Cloud, or CI scripts. Migrating production state is a big commitment for a proof of concept.

Yaffle doesn't require you to go all-in. You can use Yaffle exclusively for preview
environments while keeping your existing production workflow. This is an equal supported
steady state, not merely a migration phase.

## What you get

Using Yaffle for previews only:

- **Ephemeral environments for every PR**—real infrastructure to test against
- **Isolated state**—previews can't affect your production
- **Automatic cleanup**—resources destroyed when the PR closes
- **Plan visibility**—see exactly what will change before merge
- **Cross-workspace dependencies**—your workspaces can reference each other within the preview

What you're deferring:

- Production applies through Yaffle
- Consuming outputs from named environments (the [platform as product](/docs/concepts/platform-as-product) pattern)

## Setup

### 1. Install Yaffle

Connect your repository at [yaffle.dev](https://yaffle.dev) and add a `yaffle.toml` to your repo root.

### 2. Configure for previews only

The key: define workspaces but only trigger on pull requests.

```toml
# yaffle.toml
version = 1

# No named environments—we're not managing production
# Previews are created automatically for PRs

[[workspaces]]
path = "infra"
environments = ["*"]

# Only trigger on PRs, not pushes
[cloud]

[[cloud.triggers.github.pull_request]]
branch_patterns = ["*"]

# No push triggers—production stays with your existing tool
```

That's it. When a PR opens, Yaffle creates a preview environment and runs `plan` → `apply`. When the PR closes, Yaffle destroys the preview resources.

### 3. Namespace your resources

Preview environments need unique resource names to avoid collisions. Use the `{{ environment }}` template variable:

```hcl
# infra/main.tf

variable "environment" {
  type = string
}

resource "aws_s3_bucket" "data" {
  bucket = "myapp-data-${var.environment}"
}

resource "aws_ecs_service" "api" {
  name = "api-${var.environment}"
  # ...
}
```

Yaffle automatically sets `environment` to `pr-42`, `pr-99`, etc. for preview runs.

<Aside type="tip">
You probably already have an `environment` variable for staging vs production. The same pattern works for previews—just make sure resources use it for naming.
</Aside>

### 4. Keep your existing production workflow

Your existing tool (Atlantis, TFC, CI scripts) continues to manage production. Nothing changes there.

```
PR opened     → Yaffle creates preview, applies
PR updated    → Yaffle updates preview
PR merged     → Yaffle destroys preview
                Your existing tool applies to production
```

## Example: Alongside Atlantis

If you're running Atlantis today:

```yaml
# atlantis.yaml (unchanged—still manages production)
version: 3
projects:
  - dir: infra
    workflow: default
    autoplan:
      when_modified: ["*.tf"]
```

```toml
# yaffle.toml (new—manages previews only)
version = 1

[[workspaces]]
path = "infra"
environments = ["*"]

[cloud]

[[cloud.triggers.github.pull_request]]
branch_patterns = ["*"]
```

Both tools can coexist:
- Atlantis comments on PRs with production plans
- Yaffle creates actual preview infrastructure
- On merge, Atlantis applies to production, Yaffle cleans up the preview

## Example: Alongside Terraform Cloud

If you're using TFC with VCS-driven runs:

```hcl
# TFC workspace configured for main branch (unchanged)
# Continues to manage production applies
```

```toml
# yaffle.toml (new—manages previews only)
version = 1

[[workspaces]]
path = "infra"
environments = ["*"]

[cloud]

[[cloud.triggers.github.pull_request]]
branch_patterns = ["*"]
```

TFC runs speculative plans on PRs. Yaffle creates real preview infrastructure. Different purposes, no conflict.

## Limitations

Using Yaffle for previews only has different integration requirements:

| Feature | Customer-CI production | Yaffle-managed named environment |
|---------|---------------|-------------|
| Ephemeral PR environments | Yes | Yes |
| Cross-workspace modules (within preview) | Yes | Yes |
| Production applies | Existing owner | Yaffle-managed or existing owner |
| Named environment outputs | External publication (planned) | Managed publication; external publication planned |
| Platform as product pattern | Planned through external snapshots | Managed snapshots; external snapshots planned |

External named-environment snapshot publication is planned beta work, not a currently
available integration. The frozen contract does not require Yaffle to own that producer's
lifecycle when publication is implemented.

Within a preview, cross-workspace references work fine—your `compute` workspace can consume outputs from your `network` workspace as long as both are part of the same PR.

## Optional: let Yaffle manage named environments

If you want Yaffle, rather than customer CI, to own a named environment:

### 1. Add named environments

```toml
version = 1

[[environments]]
name = "production"

[[environments]]
name = "staging"
```

### 2. Add push triggers

```toml
version = 1

[[environments]]
name = "production"

[cloud]

[[cloud.triggers.github.push]]
ref_patterns = ["refs/heads/main"]
environment = "production"
```

### 3. Import existing state

Yaffle can import your existing state, or you can start fresh and `tofu import` resources.

### 4. Remove your old tool

Retire the old owner for that environment before enabling Yaffle applies. Never allow two
systems to own the same state. You can keep customer CI as the owner indefinitely.

## Summary

Starting with previews lets you:

1. **Add Yaffle previews** without transferring production ownership
2. **Get real value immediately**—ephemeral PR environments
3. **Reduce risk**—previews are isolated, production is unchanged
4. **Choose ownership per environment**—add Yaffle-managed named environments only when useful

Use Yaffle-managed production or keep your existing CI. Both are first-class steady states.
