## What's a workspace?

A workspace is a directory containing OpenTofu (or Terraform) files. Yaffle runs `plan` and `apply` independently for each workspace.

```toml
version = 1

[[workspaces]]
path = "infra/network"
environments = ["*"]

[[workspaces]]
path = "infra/compute"
environments = ["*"]
```

Each workspace gets its own state file, runs independently, and can have its own variables.

## Multiple workspaces

Most projects have multiple workspaces:

```
repo/
├── infra/
│   ├── network/      # VPC, subnets, security groups
│   ├── database/     # RDS, ElastiCache
│   └── compute/      # ECS, Lambda
└── yaffle.toml
```

```toml
version = 1

[[workspaces]]
path = "infra/network"
environments = ["*"]

[[workspaces]]
path = "infra/database"
environments = ["*"]

[[workspaces]]
path = "infra/compute"
environments = ["*"]
```

## Dependencies

Workspaces often depend on each other. Your compute layer needs outputs from your network layer.

Yaffle automatically detects dependencies by scanning your OpenTofu files for module references to other workspaces. When workspace A depends on workspace B:

1. B runs first
2. B's outputs become available as a module
3. A runs and can consume B's outputs

<Mermaid
  chart={`
graph LR
    network --> database --> compute
`}
/>

<Aside type="tip">
  Dependencies are inferred from your OpenTofu code. You don't need to declare them manually.
</Aside>

## Using outputs from other workspaces

Reference another workspace's outputs using the Yaffle module registry:

```hcl
# infra/compute/main.tf
module "network" {
  source = "yaffle.dev/acme--platform/infra--network/yaffle"
}

resource "aws_ecs_service" "app" {
  # Use outputs from the network workspace
  network_configuration {
    subnets         = module.network.private_subnet_ids
    security_groups = [module.network.app_security_group_id]
  }
}
```

The module source follows this pattern:

```
yaffle.dev/YAFFLE-ORG--REPO/WORKSPACE--PATH/yaffle
```

Where:

- `YAFFLE-ORG--REPO` identifies the producer repository
- `WORKSPACE--PATH` uses `--` as the path separator

Examples:

- `infra/network` → `infra--network`
- `apps/web/infra` → `apps--web--infra`

<Aside type="note">
  Only same-repo Yaffle module references become DAG edges. Cross-repo modules are valid, but they
  are treated as normal external Terraform modules and do not affect execution order inside the
  current repo.
</Aside>

## Internal vs public outputs

A workspace explicitly selects the outputs that may leave its viewer surface:

- `internal` outputs are available only to downstream workspaces in the same repo
- `public` outputs are available to explicitly allowlisted workspaces in other repositories in the same Yaffle org during beta

Unconfigured outputs remain in Terraform state and are visible only through authorized viewer
surfaces, with sensitive values redacted. They are not copied into modules, Actions, lifecycle
payloads, or shared snapshots.

The beta shared-output contract uses immutable, versioned snapshots rather than a mutable
live record. Each snapshot includes a stable snapshot ID and publication version,
producer, source revision, opaque state identity and serial, publication time, values,
and sensitivity metadata. Transport and consumer pinning are implemented by downstream
beta work.

```toml
version = 1

[[environments]]
name = "main"

[[workspaces]]
path = "platform/eks"
environments = ["main"]

outputs.cluster_endpoint = { visibility = "public", consumers = ["acme:applications:apps/*"] }
outputs.cluster_ca = { visibility = "public", consumers = ["acme:applications:apps/*"] }
outputs.cluster_name = { visibility = "internal" }
```

This means:

- workspaces in the same repo can consume explicitly selected `internal` and `public` outputs
- allowlisted external consumers only see the `public` outputs
- each consumer selector includes the target Yaffle org slug, repo slug, and workspace pattern

<Aside type="tip">
  Use `public` outputs for stable platform APIs. Keep implementation details and sensitive internals
  out of that surface.
</Aside>

Sensitive values are redacted in viewer APIs and rejected from modules, Actions, lifecycle
payloads, and public policies. Publish a secret reference such as an ARN instead of the secret
value itself.

## Intra-repo vs cross-repo modules

Yaffle treats module sources differently depending on which repo they point at.

```hcl
# Same repo -> included in the DAG
module "shared" {
  source = "yaffle.dev/acme--applications/infra--shared/yaffle"
}

# Different repo in the same Yaffle org -> external module, not a DAG edge
module "cluster" {
  source = "yaffle.dev/acme--platform/platform--eks/yaffle"
}
```

Rules:

- same-repo modules participate in dependency inference, ordering, and blast-radius analysis
- cross-repo modules resolve through the registry but do not become DAG edges in the current repo
- cross-org module sharing is unsupported in beta and planned as a post-beta enterprise capability

## Execution order

Yaffle builds a dependency graph and executes workspaces in the right order:

<Mermaid chart={`
graph LR
    network[network]
    monitoring[network-monitoring]
    database[database]
    compute[compute]
    appconfig[app-config]

    network --> database
    monitoring --> database
    database --> compute
    appconfig --> compute

`} />

Root workspaces (no dependencies) run first, in parallel. Downstream workspaces wait for their dependencies to complete.

## Run lifecycle and approval

When you open a PR or push to a branch, Yaffle executes runs through several stages:

<Mermaid
  chart={`
stateDiagram-v2
    [*] --> pending: Trigger received
    pending --> planning: Runner acquired
    planning --> waiting_approval: Plan complete
    waiting_approval --> applying: Approved
    waiting_approval --> cancelled: Rejected
    applying --> success: Apply complete
    applying --> failed: Apply error
    planning --> failed: Plan error
    success --> [*]
    failed --> [*]
    cancelled --> [*]
`}
/>

| Status             | Description                            |
| ------------------ | -------------------------------------- |
| `pending`          | Run is queued, waiting for a runner    |
| `planning`         | OpenTofu plan is executing             |
| `waiting_approval` | Plan complete, awaiting human approval |
| `applying`         | Apply in progress (after approval)     |
| `success`          | Run completed successfully             |
| `failed`           | Run failed with error                  |
| `cancelled`        | Run was cancelled or rejected          |

<Aside type="note">
  Preview environments require approval before `apply` runs. Configure auto-approval for specific
  environments in your `yaffle.toml` if needed.
</Aside>

## Workspace variables

Set variables per workspace:

```toml
version = 1

[[workspaces]]
path = "infra/compute"
environments = ["*"]
variables.instance_type = "t3.medium"
variables.desired_count = 2
```

Use template variables for environment-specific values:

```toml
version = 1

[[workspaces]]
path = "infra/compute"
environments = ["*"]
variables.environment = "{{ environment }}"
variables.domain = "{{ environment }}.example.com"
```

## Environment targeting

Control which environments a workspace runs in:

```toml
version = 1

[[environments]]
name = "production"

[[environments]]
name = "staging"

# Runs in all environments (including previews)
[[workspaces]]
path = "infra/network"
environments = ["*"]

# Only production
[[workspaces]]
path = "infra/production-only"
environments = ["production"]

# Only named environments (not previews)
[[workspaces]]
path = "infra/staging-and-prod"
environments = ["staging", "production"]
```
